ICIP-10000
=======

NOSTR Compatibility
-----

`draft` `optional`

This ICIP defines a way to achieve and maintain compatibility between NOSTR and ION Connect for all the events in the system.
### Motivation

As the ION Connect Protocol grows, we need a way to bridge the gap between present and future needs of the protocol and its origins, the NOSTR protocol.

At the moment compatibility between ION Connect and NOSTR is only unidirectional, and we aim to change that by having the ION Connect clients maintain a "pure NOSTR" version of each event alongside the ION Connect one. 

### Definition

As per [ICIP-01](ICIP-01.md#publishing-multiple-events-at-once), multiple events can be published at once, thus, each event specified MUST have a "pure NOSTR" equivalent IF that source event is not "pure NOSTR" itself.

Additionally, to optimise for bandwidth usage and storage costs, if both versions of the same event share the same content (and in most cases they should), the "pure NOSTR" event should have its content field NOT present (missing) from the event, which will be interpreted as "being the same as in the source event" (the event.id MUST still include the content field in the array of fields used in its generation).

Both pubkeys (from the source and "pure NOSTR" events) MUST be valid delegations to the same master keypair as per [ICIP-2000](ICIP-2000.md).

The "pure NOSTR" version of each event MUST be embedded in the content of a 21750 [ephemeral event](ICIP-01.md#special-ephemeral-event-for-embedding-other-non-ephemeral-events) where the `e` tag of the 21750 event is the event.id of the source event.

### Clients & Relays

Clients MUST only send the "pure NOSTR" events inside the 21750 event, not as a standalone event.

Both Clients and Relays MUST validate the input events and their relationship as strictly as possible, according to a 1:1 mapping of each pair: I.E. 30175:1, 3:3, etc. The pairs MUST be equivalent, you cannot pair, for example, kind 0 with kind 3, you can only pair ION Connect kind 3 with pure NOSTR kind 3, or ION Connect kind 30175 with pure NOSTR kind 1, etc. 

Relays SHOULD store the content once, if it's shared amongst both versions of the event.
Relays MUST return the correct version of the event based on the caller/client that's requesting it (if it's a ION Connect client or not).
