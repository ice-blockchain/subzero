ICIP-8000
======

Push Notifications
-----------------------------------

`draft` `optional`

This ICIP adds support for push notifications. Inspired by [NIP-97](https://github.com/nostr-protocol/nips/blob/master/97.md)/[1528](https://github.com/nostr-protocol/nips/pull/1528).

The support is loosely tight to using Firebase Cloud Messaging as the vehicle of sending push notifications.

## FCM Client Configuration

When client apps connect to the relay to get the information document via [NIP-11](https://github.com/nostr-protocol/nips/blob/master/11.md) we need to return the following extra fields:

1. `fcm_android_configs`
   * the returned information is a string array of all the android client app configs that relay is allowed to send push notifications to. The config is essentially the runtime version of the `google-services.json` provided by the firebase console, transformed into a specific JSON, manually, because it needs to be mounted dynamically at runtime, rather than being embedded at compile/build time.
     ###### Example of 1 element in the returned array  
     ```json
        {
           "apiKey": "API_KEY",
           "appId": "APP_ID",
           "senderId": "SENDER_ID",
           "messagingSenderId": "SENDER_ID", /* you should add both senderId & messagingSenderId fields to maximise the compatibility with client platforms  */
           "projectId": "PROJECT_ID"
        }
     ```
2. `fcm_ios_configs`
   * the returned information is a string array of all the iOS client app configs that relay is allowed to send push notifications to. The config is essentially the runtime version of the `GoogleService-Info.plist` provided by the firebase console, transformed into a specific JSON, manually, because it needs to be mounted dynamically at runtime, rather than being embedded at compile/build time. 
     ###### Example of 1 element in the returned array
      ```json
        {
           "apiKey": "API_KEY",
           "appId": "APP_ID",
           "senderId": "SENDER_ID",
           "messagingSenderId": "SENDER_ID", /* you should add both senderId & messagingSenderId fields to maximise the compatibility with client platforms  */
           "projectId": "PROJECT_ID"
        }
     ```
3. `fcm_web_configs`
   * the returned information is a string array of all the web client app configs that relay is allowed to send push notifications to. The config is essentially the `firebaseConfig` JSON provided by the firebase console.
     ###### Example of 1 element in the returned array
      ```json
        {
           "apiKey": "API_KEY",
           "appId": "APP_ID",
           "senderId": "SENDER_ID",
           "messagingSenderId": "SENDER_ID", /* you should add both senderId & messagingSenderId fields to maximise the compatibility with client platforms  */
           "projectId": "PROJECT_ID"
        }
     ```

##### The client apps MUST connect to their own fcm config.

## Registering device tokens

A new kind `31751` event is sent to the relay with the following mandatory characteristics:

1. its `d` tag set to the device id (some unique or close to unique identifier of that particular device/browser fingerprint)
2. a `t` tag set to `android`, `ios` or `web`
3. a `relay` tag set to the relay itself that receives this event
4. a `token` tag set to `nip44_encrypt(<fcm_registration_token>)`, with the receiver being the relay's keypair
5. its `content` set to a JSON array of [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md#communication-between-clients-and-relays) subscription filters `[<filtersJSON1>, <filtersJSON2>, ...]` representing the end user's choice in which events are worthy of receiving push notifications for

###### Example
```json
{
    "kind": "31751",
    "tags": [
        ["d", "<deviceID>"],
        ["t", "android"],
        ["relay", "wss://example.com"],
        ["token", nip44_encrypt(<fcm_registration_token>)],
        ...
    ],
    "content": "[
                  {
                    \"#p\": \"8e0d3d3eb2881ec137a11debe736a9086715a8c8beeeda615780064d68bc25dd\"
                  },
                  {
                    \"authors\": [\"8e0d3d3eb2881ec137a11debe736a9086715a8c8beeeda615780064d68bc25dd\"],
                  \"kinds\": [1, 3]
                  }
                ]",
    ...
}
```

##### Relays MUST NOT index the `token` tag.

Whenever an event that matches the subscription filters is published to the relay, 
it has to send a push notification to that token, if the `relay` tag is equal to this specific relay, with the stringified JSON of the matched event in the data of the push notification, in an `event` field.

##### If the push notification requires more context (I.E. knowing more details about the actor, like the relationship with the user or their profile information), it can be done so by adding the content of the [ephemeral events](ICIP-01.md#special-ephemeral-event-for-embedding-other-non-ephemeral-events) (the stringified json of the actual event it embeds --I.E. like kind 0--) published with the event itself into the `data` object of the push notification in a `relevant_events` string array field.

## Client & Relay considerations

If sending the push notification fails due to the token being invalid, Relays MUST remember that and not try to send any new push notifications to that token.

Client apps MUST update the token as soon as it changes, but no sooner than once every 8hours.

Client apps MUST try to generate a device ID that is as unique as it can be, preferably a custom UUIDv7 that is store in secure on-device storage, resistant to re-installs.
